# decode 速度数据源调查(性能浮标口径修正依据)

> 2026-10-11 · 响应"现在看看有没有办法计算 decode 速度" · 前史:2026-09-29 两案皆败(UIA 转录层 ~5s 粒度+思考盲区;stdio wrapper),tok/s 回落会话平均,等官方接口(见 [2026-09-29-性能浮标实时速度数据源选型.md](./2026-09-29-性能浮标实时速度数据源选型.md))
>
> **一句话结论**:请求级"近实时"有解且与官方 Token 调试面板同口径;逐 chunk 真流式仍无对外通道(与旧两案失败同根因)。**当日落地:metrics.mjs 回落链修正 `live ?? 最近请求 ?? 会话均值`(v0.2.71)。**

---

## 一、数据源 ranked(三档)

| 档 | 数据源 | 内容 | 判定 |
|---|---|---|---|
| 真流式实时 | renderer 事件流 `model_streaming`(text_start/text_delta/text_end 带 assistantMessageId/partId)+ `model_network_status`(started/completed/stream_stalled) | 逐 chunk 文本+事件时间戳 | **不可行**:Desktop 渲染层私有 stdio v4 协议独占,无 socket/pipe/文件镜像,MCP 面零暴露(zcode.cjs 全量 grep net.createServer/named pipe 无命中) |
| **请求级近实时** | **db.sqlite `model_usage` 表** | 每模型请求一行:`status / started_at / first_token_at / completed_at / duration_ms / time_to_first_token_ms / input|output|reasoning|cache tokens / agent / query_source` | **推荐并已落地**:decode tok/s = output_tokens×1000÷(duration_ms−time_to_first_token_ms),请求完成瞬间落库(WAL) |
| 回合级事后 | `session/debug` op(rounds[].tokensPerSecond,官方内存快照)、rollout model-io jsonl(每请求 usage+durationMs 但**无 TTFT**)、`turn_usage`、`v4/usage/stats` | 聚合 | session/debug 仅 renderer 可调;jsonl 算不了扣 TTFT 的速度 |

## 二、写入时机实测(三处,均确证)

1. **model_usage 不流式写**:流式生成期间两轮 `SELECT WHERE status='running'` 均空;全库直方图 completed=12694/cancelled=150/error=26/running=0;最近一行 completed 恰为刚结束的请求——**请求完成瞬间**落库
2. **rollout jsonl 完成后一次写**:上一回合行 completedAt 与文件 mtime 差 1ms;流式期间三轮观察大小行数零变化。行结构=请求级全量(type="model_io",无 delta/full/tail 类型行;Chat2Doc 的"full/delta/tail 缝合"数据源在别处,与该目录无关)
3. **part 表部件完成时写**:流式 18s 内最新 text/reasoning part 零更新;步骤结束时 reasoning/text/tool 三个 part 同毫秒批次出现(<35ms 间隔)——与既有结论一致("已证伪勿回头")

## 三、官方口径佐证(为何"请求级"够格当"实时")

- zcode.cjs 内部 metrics 模块的 `calculateOutputTps = outputTokens×1000÷(durationMs−timeToFirstContentMs)`——**官方定义的 decode 速度,已扣 TTFT**;仅在 `model_request_completed && querySource=main_turn` 时录入 rounds(连内部快照也是请求完成时更新,非逐 chunk)
- 桌面 UI"开发者工具→Token 调试"面板:TPS 列口径 = "Output tokens ÷ 首个输出 token 到请求结束的秒数"(i18n 字符串 `tokenDebug.tpsDescription`),renderer 以 **1000ms setTimeout 轮询**请求级数据——**官方 UI 自己就是 1Hz 请求级,不逐 chunk**
- agent 型回合中每几秒出一条新 model_usage 行 → "最近 N 秒 decode 速度"退化为"最近完成请求的 decode 速度",与官方面板粒度完全一致
- **独立旁证(2026-10-11 补)**:社区项目 xhwxt/zcode-token-usage-statusbar 的速度口径同为"最近完成请求 output÷(时长−首token)"(同读 model_usage)——与本调查结论独立趋同;其"零轮询事件驱动"靠的是 patch app.asar 注入客户端挂内部事件(非官方路线,每次更新即破坏),官方诉求见 [zai-org/feedback#1007](https://github.com/zai-org/feedback/issues/1007)

## 四、当年盲区复盘(为什么 2026-09-29 没走到这档)

1. **数据与公式当时已知**:`absorbRow` 的 `dec = dur − ttft` 就是扣 TTFT 分母,同晚还修过"NULL-ttft 行稀释平均"——缺的不是手段
2. **目标锚定 oc-tps 式"打字机中滑窗"**(240ms 粒度),两案败后注释结论记成"db 只能事后聚合"("part 表流式期间不增长"被泛化),显示直接回落会话均值——**跳过了"最近完成请求"中间档**
3. **设计意图本来就有**:stats-widget.html 第 134 行注释(2026-09-29 用户拍板)写着"流式中显示实时速度(**最近完成调用的解码率**),输出完毕切本轮平均"——live 通道死后 `tps` 回落错档到 sessAvg,没人回头补
4. **没人做官方对标**:官方 Token 调试面板 1Hz 请求级的事实,把"请求级够不够格当实时"的裁判标准拉回来了

## 五、落地设计(v0.2.71,仅改 metrics.mjs)

- `absorbRow` 增记 `lastReqTps = out×1000÷dec`(单请求;NULL-ttft 沿用 lastKnownTtft 代理;重建历史时顺序吸收,切会话/自举自然生效)
- `writeMetrics` 回落链:`tps: live ?? lastReqTps ?? sessAvg`(live 已死 → 实际生效=最近完成请求解码率;无完成请求兜底会话均值)
- HTML 零改动(▁▃┅图标/契约格式/四态动画不动):HTML 既有逻辑"流式中显示 m.tps、done 切 turnAvg"正是原始拍板口径
- 偏差声明(头注):流式中显示的是**上一完成请求**的解码率,当前请求落库瞬间刷新——请求级近实时,非逐 chunk

## 六、可证伪预测

1. 官方 Issue B(会话遥测对外暴露)若落地,`live` 通道可复活为官方事件流/订阅资源,本回落链退居兜底——**本修不与官方未来接口冲突,是它的兜底层**
2. model_usage schema 属内部格式,大版本可能变列名——每次 ZCode 大更新后跑一次 `PRAGMA table_info(model_usage)` 对账(与 rollout 格式核对同惯例)
3. 极短请求(out<10 token)的 lastReqTps 会显出噪声值(分母极小)——若观感差,加 out 阈值过滤一行即可,先不过滤保持与官方口径逐行一致
