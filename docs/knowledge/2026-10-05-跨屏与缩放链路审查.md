## 一、当前实现全链(怎么工作的)

### 1.1 跨屏切换(ZCode 从 A 屏拖到 B 屏)

```
ZCode 过界(帧级)
  └─ C# ApplyFollowGeom(每次 FOLLOW2)里 MonitorFromWindow(ZCode) 与缓存比较
       ├─ 变化 → 立即 ShowWindow(隐藏)+ _scaleHidden=true
       │    └─ OnMonChange 委托 → PS Update-UiScale(force)【不等 rescan 2.5s】
       │         ├─ Hide(幂等防御)
       │         ├─ ClearViewRgn()            ← 先撒:Rgn 撤成整窗(防"新尺寸+旧区域"错误裁剪帧)
       │         ├─ SetWindowPos(新物理尺寸)   ← 显示大小 scale:(屏宽/3840)^0.55(v0.6.38 定死 B 幂曲线,无手动调整)
       │         ├─ SetFullStage(只记值)
       │         ├─ SyncFollowNow()            ← move 窗口过屏(系统此刻可能自动 DPI 缩放)
       │         └─ MonitorFromWindow(ZCode)→GetDpiForMonitor → SetWantDpr(新屏期望值;v0.6.38 屏 DPI 源,GetDpiForWindow 仅兜底——旧写法跨屏过渡期读旧屏值=脏 wantDpr,见 4.1 v0.6.38 行)
       ↓
页面(隐藏中)经历 2-3 个布局阶段(WebView2 DPI 过渡,详见三)
  └─ 每阶段一个 shape 上报(实测几何 + 页面 dpr)
       └─ ps1 解析 → SetHitMask/SetShapeDpr → ApplyViewWindow(裁 Rgn)
            └─ 解除显示的三重判据(全过才出现):
                 ① 窗口物理尺寸 == 期望(不符则自愈重设回期望,3 次兜底)
                 ② 页面 dpr == 新屏期望值(差>0.01 不起计时,并撤销已武装的静默计时——v0.6.38 KillTimer 双保险;等 2s 兜底)
                 ③ 连续 400ms 无新 shape(布局静默;SetTimer 到期 WM_TIMER 解除)
```

### 1.2 同屏缩放(同一屏幕内调整 ZCode 宽高)

- ZCode 尺寸变化 → WinEvent LOCATIONCHANGE → FOLLOW2 → ApplyFollowGeom **仅 move**(锚定:胶囊中心 = ZCode 顶 + 高/3,标题栏避让钳制:yMin = ZCode 顶+70-胶囊顶)。
- **不触发窗口 resize**(悬浮窗尺寸只跟屏幕走,与 ZCode 宽高无关),不触发 shape 重报,不走静默链。此路径简单,历轮实测无异常。
- 容纳判定:带底(y+可见底+14)越过 ZCode 底 → 整体隐藏 + `_sizeHidden`,高度恢复自动重现。ZCode 高度 < ~1.5×胶囊高时隐藏属设计行为。

### 1.3 弹框跟随(环间滑动)

- 悬停环 → 弹窗显形(首次直报)/ 环间滑动 → `place()` 换位 + **直报 shape**(v0.6.28,绕 520ms 防抖)→ 宿主即时重裁 Rgn。
- `butler-shape-dirty` 通道为双段:立即粗报 + 520ms 精报(兜全族竞态)。

## 三、两个"为什么"

### 3.1 为什么多开 QQ/微信/B站 会加剧,现在又基本看不出来?

旧判据(纯时间:第一个 shape 到 + 220ms)看的是**时间**;多开软件 → 系统 CPU/调度压力 → WebView2 的 DPI 过渡各阶段间隔被拉长 → 原本 <220ms 的间隔拉到 >220ms → 计时器在中间态到期放行 → 症状加剧。负载是**放大器**,不是病根。

现在(v0.6.31 起)判据是**状态信号**:页面 dpr 是否已等于新屏期望值——这个不看时间,负载再大也只是让收敛整体慢一点(隐藏期稍长),不会在错误状态放行。所以"多开也不太看得出来"。

### 3.2 为什么页面要连续经历两三个布局阶段?这个设计合理吗?能根治吗?

**这不是我们的设计,是 Chromium/WebView2 多进程架构的固有行为**:

1. 宿主窗口跨 DPI 屏,系统改变窗口物理尺寸(或发 WM_DPICHANGED);
2. 宿主把新 Bounds 告诉 WebView2 → **渲染进程先收到"视口变了"** → 页面 window.resize → 第一次布局——但此时**渲染进程的 screen dpr 还是旧屏值**(设备信息由 browser 进程异步更新);
3. browser 进程的屏幕/DPI 信息同步到 renderer → devicePixelRatio 变化 → 视口 CSS 尺寸 = 物理/dpr 又变 → 第二、三次布局 → 稳定。

这个"视口先到、dpr 后到"的异步管道在 Chromium 官方 issue 跟踪里长期存在,不是宿主能单方面消除的。

**根源方向评估**(都动架构,代价大):

| 方案 | 预期 | 代价/风险 |
|---|---|---|
| A. 宿主进程上 Per-Monitor-V2 DPI 感知 | 系统不再自动缩放窗口(尺寸竞态根除),WebView2 走官方 PMv2 路径,dpr 同步更规整 | **两窗 DPI 语义全变**:stats 的"视口 CSS 恒 =winW/1.75"公式、zoom 补偿、窗口尺寸公式全要重推;风险面大,需专项 |
| B. 页面视口恒定(固定舞台 + CSS zoom 缩放替代布局缩放) | resize 时只变缩放不变布局,中间布局消失 | 页面布局模型重构(--u 自适应是 v0.6.17 基石),牵动掩码/弹窗/锚定全部实测链 |
| C. 现方案:状态判据收敛 + 静默期消化 | 中间态在隐藏期完成,零视觉暴露 | 收敛期不可见(约 0.3-1s) |

**结论**:多布局阶段**肯定存在**(Chromium 固有),"渲染过程和补全过程"可以不让你看见(现方案已做到),要让它**根本不发生**只有 A/B 两条重构路。现方案不是掩耳盗铃——显示中间态才是;收敛后显示等价于"等渲染完成再上屏",与启动页/splash 同一工程语义。若未来要做,A(PMv2)收益最大(顺带根治系统自动缩放竞态),建议作为独立专项评估。

### 4.3 结构性观察(为什么会"一直打补丁")

这条链的本质:**三个异步源(系统 DPI 缩放 / 我们的 SetWindowPos / WebView2 的多进程布局管道)以不确定顺序共同决定窗口和内容的最终状态**,每一轮补丁都是在给一个新暴露的时序窗口加判据。目前已从"时间判据"进化到"状态判据"(尺寸 + dpr + 静默),理论闭环;剩余风险集中在 4.2 清单,均为低概率边角。**v0.6.38 补一条教训:状态判据的输入源本身也会说谎**——wantDpr 原取自 GetDpiForWindow(本窗),跨屏过渡期它返回旧屏值,判据拿着假期望值照常"正确"放行(4.1 v0.6.38 行;stats v0.13m 同款坑,双窗两次踩);判据升级的下一步是审它的数据源。**根治的唯一途径是消灭异步源本身**(PMv2 / 视口恒定,见 3.2),属架构专项。
